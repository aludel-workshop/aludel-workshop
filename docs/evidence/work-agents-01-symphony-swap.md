# WORK-AGENTS-01: Symphony replaces live Work dispatch

## Owner correction and process result

The owner rejected the temporary Vision connected-key path because this packet's objective is one Symphony orchestrator for agent work across layers. A read-only comparison found reusable output formats and review rules in the old runner, but its model calls, direct record revisions and token counters conflicted with Go-pinned sessions and review-first effects. The process change applied here is to select a concrete output adapter before an action is eligible for Go. The UI and server now require an enabled, paired Symphony profile for agent staging; Go pins all supported agent batches for the worker. The old provider call is not reached from Work dispatch.

Automatic approval review rejected a broad `read`-tool-to-dispatch rule that also removed the elevated-action guard. It cited expanded agent execution and knowledge exposure. The implementation instead names explicit adapters and permits elevated Vision, Deploy review and Work review only as read-only proposals or reports with human lead acceptance. A second automatic review rejected wholesale replacement of the legacy direct-runner test file because it would discard regression coverage. The owner then approved retirement after equivalent coverage was mapped. The legacy suite was removed after the Symphony proposal and worker tests covered its still-applicable behavior.

## Concrete output paths

| Layer | Actions currently routed through Symphony | Submitted output and effect |
|---|---|---|
| Vision | `product.brief`, `product.define`, `product.clarify` | Brief claim, story acceptance and answer options are review proposals; the target is changed only after exact checked acceptance. |
| Design | `design.audit` | Read-only findings report for review. |
| Pages | `pages.a11y` | Read-only findings report for review. |
| Data | `data.contract` | Data object contract proposal; target revision changes only after exact checked acceptance. |
| Code | `platform.implement`, `platform.security` | Existing exact code candidate or security report. |
| Deploy | `deploy.review` | Read-only findings report, human lead acceptance; no environment change. |
| Work | `work.review` | Read-only findings report, human lead acceptance; no project scheduling change. |

Every adapted attempt uses the same project/profile worker token, Go-pinned task bundle, scoped knowledge search/read, one-turn reservation and Work checklist. Structured proposal submission validates action content, target revisions, used inputs, and an unchanged read-only workspace. Vision also pins the aggregate Brief revision. Duplicate submissions are idempotent; send-back and changed inputs cannot apply an old candidate. Work shows the proposal and accepts the exact ID. The Work Agents page now issues a one-time project/profile Symphony token instead of presenting an API key as the execution connection. A token alone is not readiness: the portal requires a recent authenticated worker poll (within two minutes) before showing the profile as runnable or allowing Go.

## Checks and limits

Disposable `symphony-proposals.test.mjs` passes Vision, story acceptance, Data contract, clarification, review reports in the four other layers, send-back, stale Brief, scoped HTTP submission and idempotence (**9/9**). The focused Symphony, audit and task-card tests pass (**14/14** at the 2026-09-26 checkpoint); worker readiness tests also require a recent poll rather than token issuance alone. Angular typecheck and production build pass with existing optional-chain and bundle-size warnings. The local portal was restarted with `MACHINE_SYMPHONY_DISPATCH=1`; no worker is paired for W-4's project, no Go was pressed, and no live model turn ran. The flag alone does not dispatch work.

This is **not full action coverage**: other role actions still need explicit output and acceptance adapters. Profile model/effort and provider-token limits are pinned as guidance but are not enforced by the Symphony host or metered by Aludel yet. The owner approved retiring the obsolete direct-runner suite after coverage was mapped; the replacement Symphony suite and worker recovery tests pass. The broad portal server run passed **108/109** tests. The sole failure is an unrelated tracked-script executable-bit check for `apps/portal/tools/delete-project.mjs`; its existing 100644 mode is outside this packet. The new Elixir proposal tool was edited but could not be compiled here because Elixir is not installed; a live host run and owner browser review are also outstanding. The owner must pair a worker for Browser Buddy before W-4 can stage.

## Retrospective

The temporary connected-key bridge made a single action usable but concealed a second execution system. Inspecting the real W-4 task and Symphony worker first would have revealed the pairing prerequisite before implementing Vision. The explicit-adapter rule prevented a blanket authorization expansion and gave each output a concrete review boundary; disposable tests support the rule for the listed actions only. The remaining work is to finish action adapters, compile the Elixir overlay on the pinned host, pair a real profile, and run an owner-observed W-4 turn. The profile/runtime mismatch changes the next implementation priority: host model/effort selection and measured budgets need their own contract before profile tiers are claimed as working.

## Legacy regression mapping and owner approval

On 2026-09-26 the owner explicitly approved retiring the obsolete direct-runner tests after equivalent coverage was mapped. The new proposal suite covers personal versus agent staging, blocked and unsupported actions, profile batch binding, Go without a direct model call, manual task brief in the pinned card, exact review, answer options, send-back, stale Brief, and idempotent acceptance. `symphony-worker.test.mjs` covers worker scope, skip/stop restaging, restart persistence, run reservations and extension; `security-audit-worker.test.mjs` covers blocking questions and answer/re-Go. Provider-key rejection, legacy provider model listing and token accounting are retired behaviors; they are not claimed as Symphony controls. Host model/effort and token metering remain explicit gaps above.
