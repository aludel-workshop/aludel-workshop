Two ways to organize the workspace

A · Recommended

Stable product areas, connected work

Product and design remain easy to find after a change is finished.

Projects → selected projectShared structure; each app keeps its own choices.
OverviewOutcome, attention and latest result
ProductDirection · Roadmap · Features & stories
DesignViews & journeys · System · Explorations
WorkRequests & proposals · Plan · Active · History
ReviewsExact result · Compare · Context · Response

Utilities: Decisions, Sources, Project settings. Later: Releases and Insights when their capabilities exist.

Tradeoff: more areas; strong contextual links must keep a small change quick.

B · Alternative

One workspace per change

Each request carries its brief, exploration, execution and result together.

Projects → selected project
Overview
Changes → selected changeBrief & decisions → Explore → Plan & execute → Review
Product libraryVision · Roadmap · Features · Views · System
Sources & settings

Tradeoff: a tight request-to-result flow, but shared views/components can become buried behind the last change. The same typed record foundation is still necessary.

Recommendation: A, with a compact change trail connecting intent → decisions → work → result. Keep one editor per object. Roadmap and Work are different views of the same plan, not competing task systems.

Walk the jobs you described

Open each walkthrough. These paths describe intended behavior and the check that would prove it; they are not current feature claims.

1. Find completed and future work

Work → History → B-02 → evidence → B-03 remaining plan. Completed packets carry original source evidence and limitations. Planned work has dependencies and priority. Neither invents an old authorization.

Check: find B-02 without raw Markdown; distinguish a cancelled old work item from its current replacement; return to the same collection after opening either.

2. Present and change the product vision

Product → Direction → edit draft → compare → save revision → affected plans. Readable vision, audience, outcomes and constraints. Save changes intent; it does not authorize work.

Check: only consumers of the changed constraint require reassessment; a conflicting edit retains the draft; saving unchanged text does not invalidate work.

3. Find a concept and its design-system context

Design → Views → Task detail → Explorations → selected option → system pattern/story. See the question, alternatives, image, source revision and exact scope of selection. Tokens and components retain repository authority.

Check: distinguish a selected concept from accepted interaction behavior. An expired preview remains identifiable and is not silently replaced with “latest.”

4. Ask why about a view or component

Review → Inspect context → choose view/component → intent, decisions, concept, work and checks. A keyboard-accessible list supplements pointer selection. Context is tied to this build, not just current product records.

Check: an old candidate shows its old governing decision, alongside the newer current revision. Missing rationale is named rather than guessed. Returning preserves the preview route and selection.

5. Review a change inside the whole app

Baseline + scoped change → separate candidate build → focused comparison → neighboring views → response. Use the actual project shell and components, with isolated fixture data. Stories cover local states; app builds cover journeys.

Check: the changed view sits in the real app context, unchanged UI is not separately recreated, and scenario reset preserves review notes. Candidate and trusted portal stay isolated.

6. Start another independent app

Projects → New project → rough brief → draft → scoped setup plan → authorize scaffold → review independent app. Stack, system, shared assets and providers are explicit choices, not inherited from Aludel.

Check: draft creation has no provider effect; two projects cannot leak records; the generated app runs without the portal. BorrowBox rehearses this structure but is not proof of a real second product.

“Why?” needs a recorded chain, not a plausible explanation

Outcome→Feature / story→View / component use→Decision & concept→Work & checks→Exact build

A component can support several views. A build records the revisions it used. The portal owns mutable product records and review history; repositories own code, tokens and executable stories; immutable assets retain hashes and availability. Sources stay visible as evidence.

What the first audit actually found

  • Markdown import does not create roadmap packets, view records or image assets.
  • Knowledge search currently covers titles and paths, not full source text.
  • Several APIs and imports assume Aludel is the only project.
  • Historical system catalogs and current implementation need explicit reconciliation.
  • Work’s missing list/detail navigation escaped a single-item test. The repair now passes a two-item browser journey, lifecycle, narrow-layout and accessibility checks.

Choose A with the planning/history slice, choose B and adapt the slice, or request a revised structure. Add any priority correction in the decision rationale. This selects organization and sequence for detailed design—not every page composition.
