# What exists, what is usable, and what must become a product record

This is a local source/behavior audit, not a claim that the recommended features are built. Input identities are recorded in `manifest.json`. The original portal request and proposal revision 2 remain the authoritative intent; this document analyzes them without replacing them.

## Findings that change the plan

1. **Document import is not domain migration.** [The importer](../../../../apps/portal/server/importer.mjs) imports Markdown under `docs`, taking a top-level ID and status or inventing a path ID. It does not turn execution-plan subsections, decision-register rows, design catalogs or image files into usable product objects. Markdown links become file relationships, not “this work implemented this view at this revision.”
2. **Knowledge is narrower than its promise.** [The API](../../../../apps/portal/server/server.mjs) searches source titles/paths, not arbitrary source text; [the UI](../../../../apps/portal/src/app.html) shows metadata and raw text. It neither displays image concepts in their feature context nor opens linked non-Markdown assets as reviewable artifacts. Sources are useful audit evidence, but the owner still has to reconstruct meaning.
3. **Several product objects are absent.** [Storage](../../../../apps/portal/server/storage.mjs) has projects, requests, proposals, decisions, source revisions/links and two-kind downstream records (`plan`/`build`). [Workflow](../../../../apps/portal/server/workflow.mjs) adds JSON-backed work items and events. There are no native outcomes, features, views, design systems/assets, milestone plans, artifact manifests or review records.
4. **Projects are not yet a real runtime boundary.** Source import, proposal creation and seed data use `the-machine`; list APIs are not project-filtered; the UI parses routes around one project. The presence of a projects table and a fictional BorrowBox allocation is not project isolation. Do not expose a New project wizard before fixing that boundary.
5. **Current and historical evidence disagree in places.** [Status](../../../status.md) and ADR-012 record M1/local Angular adoption; older paragraphs in architecture, roadmap, tool registry and capability allocations still describe M0 or framework selection as pending. “Latest modified document wins” would import the wrong meaning. Preserve dated assertions and their scoped supersession.
6. **Design-system identity is historical, not a live registry.** [Catalog v3](../../portal-system/v3/catalog.json) points to `prototypes/d-01f/src`; current components live in `apps/portal/src`. The accepted philosophy survives; the historical catalog is not a verified mapping of every current implementation. Component migration/lineage must be reconciled explicitly.
7. **Prototype duplication has a concrete boundary.** Separate `prototypes/d-01b`, `d-01f`, `d-01e` and `apps/portal` contain their own application assemblies/styles. This proves multiple copies exist; it does not measure maintenance cost. Treat them as versioned historical experiments. Future implementation previews should build a changed project revision using its actual shell and components.
8. **A single-record workflow test missed a basic owner journey.** The Work collection rendered all full details; [the repair/post-hoc](../../../evidence/b-03a-work-navigation.md) documents the issue and observed fix. Broader design must cover navigation/cardinality before claiming a feature usable.
9. **Seed data can overstate provenance.** `ensureB02Fixture` inserts `PROP-MACHINE-001` as accepted and `DEC-MACHINE-DATA` with author `owner`. Those are seeded summaries of bootstrap choices, not newly observed owner actions in the app. Preserve them and audit their sources; future import must identify seed/historical provenance explicitly. Do not infer acceptance from a populated field alone.

## Reconstruction test: if no bootstrap directory existed

The proposed minimum is not a document editor with more tabs. The portal needs create/revise/link/review operations for product brief, outcomes/milestones, features/stories, views/components, research/decisions, design assets/experiments, plan entries and executable work. Repository creation and component code remain specialized work with reviewable outputs. A record can be incomplete; absence and unresolved questions must be visible. It should be possible to start with one paragraph and incrementally add these objects, rather than filling the whole capability catalog as a wizard prerequisite.

Recommended first delivery does not implement every type. It establishes project scope, typed provenance and a read/write Plan spine, then expands in reviewable slices. Full arbitrary workflow editing, semantic search, team permissions and provider shopping remain deferred. [Delivery plan](delivery-plan.md) names boundaries and falsifiable checks.
