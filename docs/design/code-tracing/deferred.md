# Code tracing: removed, and boxed up for a later phase

## Decision

Owner, 2026-10-02, during JOURNEYS-01: "we're pulling the tracing. box it up, lets revisit at a later phase. don't need it mvp, too much distraction without enough clarity to add value." Asked how far, the owner chose "remove entirely. truth is, those links were not following our new binding approach anyways."

The removal is in the [JOURNEYS-01 run log](../journeys/work-record.md#run-log). The last commits with tracing are this repository's `3bdc95b` and `layer-base` `code` `cc30be2`.

## What was removed

Code links (LAY-07D, from [DEC-038](../../decisions.md) "code links to knowledge") said why each code unit existed, anchored to a knowledge record's revision.

- **Where links came from:**
  - the scaffold's generation manifest;
  - `Implements:` commit trailers;
  - test names (`S4/2 · …` for a story's scenario);
  - person-made links in `.aludel/outputs/trace-links.json` (the template's `trace_link` kind).
- **What links drove:**
  - unit states (current, suspect, untraced);
  - a Reconcile Work item when a linked record moved to a new revision;
  - `builtBy`, which fed several views:
    - Pages' *Built* status;
    - Data object and operation status;
    - Vision's "Built by" chips;
    - the stories a release *Ships*;
    - a guard against deleting built pages;
  - Code's "Stories: code and tests" panel and story-scenario test coverage.

**Why it went:**
- It is a hard-coded story ↔ code pairing, not a binding (LAYER-BINDINGS-01).
- It depends on conventions that people and agents forget (trailers, test-name prefixes), so it reports confident wrong links and noisy "untraced" glue.
- Unit granularity against story-level records makes "suspect" fire too widely to act on.

**What stays:** code units, Explorer and reachability ("Unused") are code structure, not tracing.

## Design to revisit (not decided)

From the JOURNEYS-01 discussion, 2026-10-02. None of this was accepted. It is the starting point for the later phase.

1. **Observed, not declared.** Run each journey step's test with coverage and record the units it executed. The trace is generated. "Suspect" becomes precise: a changed step makes the units observed in that step suspect.
2. **Review where it matters.** Intersect a change's units with each step's executed units: "changed code runs in steps 3 and 5 of onboarding". Invariant work (refactors, dependency bumps) would get a targeted walk instead of a diff.
3. **Entry points for full coverage.** Code is only entered by a person (UI), a client (API) or a clock or event (job, webhook). One possible model generalizes journeys to any actor, with step kinds `visit` / `call` (an `operationId`) / `event`, so entry points cover all reachable code. *Substrates* (components, schema, environment) are covered by the journeys that execute them, with their own proofs for direct changes.
4. **Attribution and gaps.** Code that doesn't execute (migrations, Dockerfile, CI, styles) would be attributed by path to a substrate. Code that no thread reaches would be a gap, raised as one deduplicated *Assess uncovered code* item per sync.
5. **Import bootstrap.** Observed single-step smoke journeys per UI route, API operation and scheduled job give an imported app a coverage map on day one.
6. **Stories connect only through journeys** (`step.story`). Code would link to journeys, never directly to stories.

**Open questions for the later phase:**
- one journey primitive with step kinds, or a separate operation contract;
- coverage adapters beyond JavaScript and Node, with a static route-level fallback;
- whether gaps raise Work or only show in Code;
- how *Built* status returns to Pages and Data. Likely from the user-journeys binding: a page is built when the journey steps on it are implemented and proven.

**What would make it worth doing:** reviews where people can't tell which steps to re-walk after an invariant change, or real projects where dead or orphaned code becomes a measurable cost.

## Interim consequences

- **Pages status.** Pages show *Planned*, *Skeleton* (generated by a build) or *Specified*, from their own record. *Built* is gone until the user-journeys binding supplies it.
- **Pages routing.** Pages no longer switch a page to change requests once it is built. Spec edits save directly, and "Request as a code change" or "Request a change" is always offered. A designer has to choose the request explicitly when the app should follow, until the binding raises Code Work from spec changes.
- **Pages view.** The running-app view (now "App") is always offered. Its existing "isn't in the running app yet" message covers pages the build doesn't have.
- **Data status** is *proposed* or *contracted*. **Releases** name no stories, and Deploy releases no longer carry stories.
- **Page deletion.** Deleting a page is still blocked once it is past *planned* or in the navigation, which a build already ensures for generated pages.
- **Older forks.** The host SDK keeps `@aludel/host/built-by` (renders nothing), `ctx.builtBy()` (always empty) and the unit `state`/`links` shape (current or unused, no links). Layer views forked before this, which existing installs keep because template updates don't reach them yet, still compile. Delete these once template updates exist.
