# Portal foundation feedback — 2026-09-19

## What the review established

The owner found D-01B version 3 significantly clearer than earlier prototypes. The opening composition from direction B works as a starting hypothesis: consequential decisions appear first and ready work appears beneath them. BorrowBox also successfully separates the portal from the application it is creating.

The rest of the flow is not ready for interaction prototyping. The prototype advanced from one promising composition into page and component choices that had not received the same design treatment.

## Findings

| ID | Observation | Design implication |
|---|---|---|
| F-01 | After recording a decision, the replacement panel reads partly like task completion and partly like a personalized decision follow-up. | Define post-decision outcomes as a transition pattern. Decide whether the owner stays in the decision context, sees the next decision, or gets a compact confirmation with explicit destinations. Do not use a generic empty/success card. |
| F-02 | A component summarizing multiple ready tasks links directly to one particular task. | Summary components must preserve the level they summarize. A ready-work summary should normally open the Work collection; a decision-specific follow-up may link only to work affected by that decision and must say why. |
| F-03 | The task page has no clear user-story spine or dominant job. | Define who arrives, from where, what question the page answers, and its state-dependent primary action before laying it out. |
| F-04 | The task-level menu looks like tabs but jumps among bento sections on one page. | Choose one navigation model: routes/subpages, in-page sections, or progressive disclosure. Do not visually imply one model while implementing another. |
| F-05 | Unrelated ready work appears on a task-detail page. | Collection-level context belongs on Overview or Work. Task detail contains only that task's intent, dependencies, authorization, current attempt/result, and history needed to act. |
| F-06 | Navbar, page layouts, and transitions contain many unreviewed product decisions. | Define the shell and a small page-layout system before another end-to-end prototype. Test hierarchy and findability using cheap wireflows. |
| F-07 | The design process still skipped stages to reach functionality. | D-01B fails its current review gate and pauses. The next packet must produce and review the missing structural artifacts before interaction code resumes. |

## Accepted, rejected, and still open

**Accepted as a direction to retain:** BorrowBox as the demo application; direction B's opening hierarchy of decisions followed by ready work.

**Rejected in the current prototype:** the post-decision completion card, direct jump from a multi-task summary to BB-001, the task-detail composition, section links styled as tabs, unrelated-work card on task detail, and any inference that the present navbar or page layouts are accepted.

**Open:** which global and project destinations exist; whether the opening composition belongs on Project Overview or Decisions; what appears immediately after a decision; the Work collection structure; task-detail stories and layout; authorization placement; review entry and layout; responsive navigation; Q-004 and Q-005.

## Root cause

The existing experience foundation named destinations and reusable patterns, but those labels were treated as sufficient design. It did not prove the owner journeys, define page archetypes, specify what each page owns and excludes, or compare shell/layout alternatives. D-01C explored one Overview composition while assuming the rest of the product structure. D-01B then encoded those assumptions.

The next work must move back from interaction implementation to product structure. The desired output is a small coherent system of places and transitions, not another polished screen.

## Gate for another prototype

Before D-01B resumes, the owner must be able to review:

1. a product map and navigation rationale across the first useful loop;
2. the owner journeys for Decide, Authorize, Follow, and Review;
3. page archetypes and responsibility boundaries, including collection versus detail pages;
4. the post-action transition rules for decisions and task authorization;
5. task-detail stories by state and a content hierarchy derived from them;
6. at least two shell/layout alternatives and wireflows for the selected journeys;
7. a component inventory whose components each trace to a page responsibility and story.

No interaction code is required for this gate. Paper-level diagrams, text wireframes, or static HTML boards are sufficient.
