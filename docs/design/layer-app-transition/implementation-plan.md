# Run Aludel on the layer-app model: isolated implementation plan

## 1. Outcome, scope, and evidence boundary

Build a **candidate Aludel** from the current portal in a separate Git worktree and runtime. Keep the current Aludel available while the owner repeats comparable journeys in both. The candidate should use layer-owned outputs, knowledge, routines, and reviewed connections, while Home, Library and Work remain shared project services. The first conversion is **Pages**, retaining its built Map / Pages / Flows experience rather than copying the trial's simplified editor. Then prove one adjacent local layer (Vision) and one reverse-input relationship (Code observations → Pages), and convert the remaining built-in local layers before full comparison. A successful candidate can be considered for promotion only after the owner reviews its usefulness and the migration/recovery evidence.

This plan is **not** approval to replace the running portal. [Prototype v3](../layer-app-trial/v3/index.html) proves navigation and a simulated lifecycle; it does not prove durable records, real agent runs, access control, migration, or usefulness in an owner design session. [DEC-048](../../decisions.md) governs the built Pages behavior; [DEC-050](../../decisions.md) governs Work items and runs. This plan should preserve both unless an explicit later decision changes them.

**In scope:** local layer instances and descriptors; output/API projections over existing typed records; standard Operations and Knowledge surfaces; versioned routine and connection documents; deterministic utility scans; bounded agent routine Work items through the existing Work contract; Home layer management and optional dashboard cards; migration and comparison of local project data. **Deferred:** Figma/external layer adapters, arbitrary third-party layer installation, hosted multi-instance sync, production release, spending, and autonomous execution beyond the present Work authorization model.

## 2. Isolation topology and operating rule

Use a sibling Git worktree on a dedicated branch, provisionally `../aludel-layer-model` on `feature/layer-app-model`. Pin the starting commit and record it in the candidate work record. A sibling path avoids nested repository scans and accidental corpus import. The candidate must have an ignored, independent data directory and a dedicated launch command. The checked-in `./launch-machine` is **not** safe for candidate startup as-is: it reads the checkout's `.env` and calls `integrations/symphony/local-hosts` before starting the server. LAT-01 supplies a candidate launcher that explicitly sets local-only configuration, never reads the current checkout's `.env`, never starts local hosts, and refuses a data path inside the current portal's `.data`.

| Boundary | Current Aludel | Candidate default / proof |
|---|---|---|
| Code | Current checkout and branch | Pinned sibling worktree and candidate branch; no edits to current checkout during candidate packets. |
| Portal address | Existing `aludel.localhost:4310` | Proposed `aludel.layers.localhost:4311` using `MACHINE_BASE_DOMAIN=layers.localhost`, `MACHINE_PORT=4311`, `MACHINE_PUBLIC_PORT=4311`; verify local resolution and host classification before promising this URL. |
| Data and artifacts | Current `apps/portal/.data` or configured path | Candidate worktree's ignored `.data` via an explicit absolute `MACHINE_DATA_DIR`; own SQLite, preview workspaces, logs and secret store. |
| Sessions | Current portal host | Distinct candidate hostname and session store; confirm cookies do not cross origins. |
| Workers | Current Symphony pool/containers | `MACHINE_SYMPHONY_DISPATCH=0` initially; candidate launcher does not invoke `local-hosts`. Later Work tests use local stand-ins or a separately named disposable pool only after a packet authorizes them. |
| External accounts | Existing local credentials/configuration | Do not copy `.env`, secret-store files, tokens, GitHub bindings or worker credentials. Connector controls are unavailable in the candidate until independently authorized. |
| Project data for comparison | Current records | Start with a deterministic fixture. If needed, later use an inspected, redacted SQLite backup created through SQLite backup semantics, not an uncoordinated copy of a live WAL file. No candidate write reaches current state. |
| Generated app previews | Current project workspaces/ports | Candidate preview directories and project IDs remain in candidate data; validate no preview host/port collision. |

**Isolation gate:** both servers start together; their session cookies, databases, Work items, files, preview ports and logs remain independent. A mutation in either one is invisible in the other. Stop and repair isolation before any domain migration if this fails. Comparison is performed on matching fixture scenarios and recorded source revisions, not by assuming independently edited databases should remain equal.

## 3. Shared architecture and authority

A layer app is a **domain boundary in one portal process**, not a required microservice. The shared kernel provides identity, permissions, typed discovery, revision/event delivery, routine scheduling, provenance, and Work handoff. Each layer supplies its own output validators, projection, quality policy and renderer. Keep the existing `knowledge_records` / `knowledge_revisions` and domain validators as authority for product artifacts; do not replace them with an unrestricted generic entity store. Extend the existing `routine`, `routine_runs` and `layer_work_items` contracts where possible. The candidate may add normalized tables for layer instances, connection policies, trigger receipts and gap observations where existing records cannot express their lifecycle.

| Boundary | Owner | Concrete candidate contract |
|---|---|---|
| Home | Shared project shell | Order/manage active local layer instances and optional bento cards; summarize work and health using read models; never author another layer's artifacts. |
| Layer output | Owning layer | Stable kind/ID/revision, typed validator, writer authority, project scope, links, human view and machine descriptor. Pages owns `page_map`, `page`, `flow`; Vision owns Brief/story records. Code projects Git facts without claiming Git bytes belong to the portal. |
| Layer knowledge | Owning layer | Tree of output specs, methods, expert instructions, routine definitions and connection documents. Each node has a stable ID, revision, author/source, visibility and retrieval scope. Existing repository rules remain in Git; database documents do not silently supersede `AGENTS.md`. |
| Connection | Receiving layer | Versioned document naming source layer/output type, applicability and correspondence rules, change response, evidence, question/decision and reviewer; states `proposed`, `active`, `degraded`, `retired`. Discovery proposes; review activates. |
| Routine | Owning layer | Definition pins executor (`utility` or Work agent action), trigger, instruction-document revision, allowed reads/effects, output kinds, quiet period/cadence and enable state. Every run is represented by a Work item and a run record with exact inputs, outputs, outcome and errors. |
| Reconciliation | Owning layer, shared scheduler | Durable trigger receipt; compare exact source/policy/output revisions; stable gap key; stage/resolve linked Work once; retain intentional exceptions and rejected proposals; never delete accepted outputs when a source vanishes. |
| Work | Permanent control plane | Existing item/run/Go/review/attempt contracts own authorization, questions, agent execution, budgets, effects and reviewer decisions. A routine cannot widen its own capabilities or dispatch itself. |
| Library / gateway | Permanent shared evidence and retrieval | Library owns sources, findings, insights and human search. Project-scoped knowledge discovery resolves layer descriptors and revisions under role permissions; it does not take authorship of layer outputs. |

**Minimum layer declaration:** stable layer key and project instance; output kinds and validators; authority; layer-owned actions with exact permissions, initial-assignment styles, checks and output adapters; knowledge root; routine definitions; input/connection capabilities; health/coverage projection; UI work surfaces; migration/export version. [DEC-051 groundwork](../work-agents/layer-owned-actions.md) supersedes the one-role-per-layer action catalog; Work still owns Go, attempts and review. A versioned descriptor API lists only permitted types and their counts/summaries. Fetching exact records remains a scoped operation. Neither the descriptor nor a model response grants write authority.

**Agent boundary:** keep the [Go-pinned manifest](../work-agents/session-contract.md) and exact review boundary. A discovery agent can propose a connection or ask a question; a sync agent can stage Pages work under accepted policy; a Pages expert can propose a flow. The accepted connection and source revisions are pinned on each run. Policy changes create a new revision and affect future runs, not a running attempt. A utility may close an untouched, resolved suggestion under an explicitly checked rule; a touched/authorized item needs Work's existing state and review rules.

## 7. Risks, decisions, and reversals

- **Knowledge authority:** DEC-047 defers the long-term companion-repository/sync choice. This local candidate may store mutable layer policy/docs in its isolated SQLite database with portable export; it must not claim this settles cross-instance authority. No multi-instance sync packet is hidden here.
- **Schema generality:** use built-in typed declarations and validators first. If Pages/Vision/Code cannot fit the shared lifecycle without special cases that corrupt authority, narrow the kernel. Do not open arbitrary record kinds merely to make layer creation appear generic.
- **UI inheritance:** v3 prototype is an agent-checked trial direction only, while the built Pages, Design and Work decisions have different acceptance scopes. Reuse current production components and check its design system; no prototype CSS copy is an implementation criterion.
- **Routine churn:** a page may be linked five minutes after creation. Immediate utility closure is safe only for a specific untouched gap; task creation needs a documented quiet period, cooldown or explicit scan. Track suppressions and rejected mappings so scans do not nag repeatedly.
- **Run recovery:** a trigger is not permission. Persist trigger/run identity before scheduling and let Work own retry/recovery. Never re-dispatch an uncertain external attempt because a browser reload or source event repeated.
- **Divergent branches:** current Aludel may continue changing while the candidate develops. Rebase in bounded intervals with a migration/parity rerun. Do not compare a stale candidate to a newer current build without recording both commits and schema versions.
- **Sensitive state:** current SQLite and ignored data may contain private project information or encrypted references. Inventory and redact before any copied fixture; never copy secret-store files or print credentials into evidence.
- **Reversal signals:** if the shared Operations/Knowledge slots make a layer's work harder to find, if policy review generates low-value chores, if Code observations are consistently misread as intent, or if typed declarations need repeated unsafe escapes, revise the model before adding more layers.

## 8. Review, promotion, and stop rules

The candidate has three different approvals: (1) **experience**—the owner prefers the journeys; (2) **data/behavior**—migration and authority tests pass on a copy; (3) **release**—the owner authorizes the exact cutover and any external effect. Approval of one does not imply another. Before LAT-10, the current portal remains the operational version. Candidate sessions, Work and project records are disposable and do not sync back automatically. Do not promote a candidate database over the current database as a shortcut.

A promotion proposal must name the code commit, candidate schema migration IDs, source database backup identity, affected projects, known exclusions, release window, health checks, abort threshold, fallback version, and restore rehearsal result. Prefer backward-compatible expand migrations and a bounded recovery window. If a migration is not reversible, rollback is restore from the pre-cutover backup plus replay/reconciliation of authorized writes after it—not merely switching code back. The owner makes the final transition decision from this concrete evidence.
