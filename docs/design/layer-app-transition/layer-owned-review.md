# LAT-08A — review changed layer views

## Owner intent and boundary

The owner wants the layer that created a Work item to own its review experience. Work remains the shared ledger for task criteria, Go, runs, performer evidence, reviewer signature and atomic acceptance. The originating layer supplies the review composition and reviewer policy; each changed output is validated by its own layer before atomic acceptance. If a Pages relation to a Code observation creates the task, Pages owns its review; Code supplies the pinned source evidence. Record the origin layer at item creation and pin it for the run. A cross-layer task may show evidence from other layers, but it does not transfer review ownership or grant another layer authority over the resulting output.

The reviewer's main question is “what would this layer look like if I accepted this run?” Show the affected native layer tabs with proposed changes highlighted. The review render reads a retained candidate snapshot or typed proposal at a pinned revision. It never changes accepted records or asks a live current tab to display unapplied changes. A **Previous / Proposed** switch shows both states using the same tab and stable viewport/selection where possible; changed objects are marked and linked to criterion evidence. The review shell also retains a concise change list for orientation, flags and navigation. No universal standalone Preview tab is required. If a change has no native renderer, show an honest typed before/after view and name the missing layer surface.

| Origin and output | Review view | Evidence that stays distinct |
|---|---|---|
| Design tokens/components | Design's affected Tokens or Components tab, with changed values and contextual examples; a sequence of examples can read like a slide deck inside Tokens | Token/component validation and visual checks tied to the candidate revision |
| Pages pages/flows | A focused slice of Map, Pages or Flows with changed nodes, paths and states highlighted | Source story or Code observation remains linked evidence, not proof of intended flow |
| Code candidate | Code Explorer shows changed files/units and diffs; Code Tests shows **results of the candidate's actual runs**, with status, logs and revision | Code's **Local app** opens an isolated runnable candidate for clicking through with synthetic data; it is a normal Code tab as well as a review view |

The Code Local app tab is useful outside Work review for the current development copy. In review it selects the retained candidate build; Previous selects a separately identified baseline build if available. Show source commit, build identity, data fixture, availability and failure reason. Keep synthetic data and its session outside the trusted portal origin. A non-web project or failed build shows an unavailable state and its checks; no fake preview is rendered. This extends Code's existing reference role without turning Code into an editor.

## Simple repository-read default

Code owns the project repository as a versioned output and is the gateway for reading it. An authorized project Work actor/action may read the **full bound project repository** through Code by default; LAT-08 does not need per-action path allowlists for reads. Code checks project/repository binding, membership or explicit action grant, and source revision; the request cannot reach another project's repository or host files. Existing credential/secret exclusions still apply, including ignored or untracked local secrets. Repository writes, candidate commits and external effects remain separately authorized and checked. A receiving layer cites Code's file/revision identity rather than taking ownership of repository bytes. This revises DEC-051/053's proposed per-path read detail, not their project boundary or explicit write/effect gates.

## Packet contract and checks

**Prerequisites:** LAT-07 supplies the native Design, Pages and Code tabs and action inventory; LAT-08 supplies the origin/action migration, project grants and Code read gateway. Reuse DEC-050's run/review signature and retained candidate snapshot contracts. Do not start from visual tab names alone; map each affected output kind to its authoritative renderer and apply validator.

**Build:** record pinned origin layer and affected output/tab references in the run; define a layer review renderer interface for accepted and candidate revisions; compose only affected tabs in the shared Work review shell; add Previous / Proposed, change focus, criterion evidence and unavailable/stale states. Adapt Design, Pages and Code, including Code test results and the Local app development copy. Preserve atomic accept/reject and historical run snapshots.

**Acceptance evidence:** with disposable isolated data, review one Design token change, one Pages flow change and one Code change. For each, switch Previous / Proposed without mutating the accepted output, navigate the changed native tab and check its revision/criterion link. Code Tests must show a real candidate test result, and Code Local app must run with synthetic data both from Code and from Work review. Reject one run and confirm nothing applies; accept a separate current run through the owning layer validator and verify one atomic change. Change the source/action or candidate revision and verify stale review blocks acceptance. Test a missing renderer, failed build and non-web project as explicit unavailable states. Check owner/member access and wide/390px keyboard/a11y behavior. The owner then judges whether the reused tabs make review clearer in LAT-09; agent checks alone do not establish usefulness.

**Stop condition:** no candidate snapshot, origin layer, revision or authoritative validator means no Accept. A missing Local app does not block a non-web action when other required criteria are met; it must remain visible as unavailable evidence rather than a fabricated preview.

## Code preview lifecycle proposal (2026-10-02)

**Scope:** owner-requested local research and planning, recorded in the [T03-CODE run log](t03-code-brief.md#run-log). Proposed defaults below are not owner acceptance or implementation authorization. T03-CODE remains the single next action.

**Process improvement:** assess retained artifact storage separately from active runtime capacity. Require a ten-candidate lifecycle trial before claiming the preview path scales. Code reviews must retain submission identity independently of worker workspaces and mutable app data. Existing architecture already requires this; the missing planning detail is lifecycle and resource evidence.

**Recommendation (revised after the merge/build discussion):** retain source submissions and agent check evidence on submission; prepare the combined build when review is opened. Combine the submission with the latest accepted repository head in isolation, validate it, and for runnable Code changes build/test/preview that exact combination. Reuse build/check evidence only while its source, environment and consumed inputs remain identical. Route generic Code Work through a host candidate/build capability reused from the existing candidate path, without restoring legacy action IDs. The Code template supplies its Local app review view; the host controls isolation, identity, scheduling and cleanup. Initially serialize builds, allow two running previews (including Previous/Proposed), and stop idle runtimes after a proposed ten-minute interval with no active viewer lease. These are trial settings, not measured capacity limits.

**Identity and data:** retain submission ID, base/candidate commits, exact image digest, dependency lockfile, fixture revision, environment recipe and checks. Revised submissions create new identities. Each running candidate gets a separate writable data store seeded deterministically by its own versioned app migrations/fixture recipe. Reset restores that recipe. Fixtures are maintained with schema changes; Data-owned contracts are consumed through pinned Library references. Previous uses its compatible fixture, and comparison names differing fixture revisions. Cover empty, ordinary, permission and error states. Synthetic identity and service adapters avoid live mail/payment effects. Never share portal or accepted-app data/cookies with candidates. Dependency changes may require new shared image layers; rebuilding an evicted artifact is new build evidence, even from the same commit.

**Storage and retention:** unopened reviews retain source submissions and existing evidence; reviews opened for runnable Code changes additionally retain their combined image and small synthetic data. Runtime memory is allocated only to open previews. Disk includes shared image layers, each candidate's unique layers, worktrees, data, logs and build cache. Cap data/log/cache growth, track attribution, and retire closed/superseded build artifacts after an explicit grace period. Keep source commits, fixture recipes, digests and review evidence. Under disk pressure, expose expiry or pause new builds rather than silently replacing the artifact behind an open review. App-defined environments and multi-service apps remain PP-01D dependencies; do not claim the preset runner supports arbitrary imported apps.

**Evidence/readiness:** [T03-CODE evidence](../../evidence/t03-code/README.md) records the generic-path preview gap. Source inspection of `apps/portal/server/code-candidates.mjs` and `previews.mjs` confirms retained candidate worktrees, candidate-specific runtime/data support and restart-on-demand, but no idle timer/global quota. The runtime currently uses image tags; acceptance-grade digest identity needs explicit handling. Docker documents [shared image layers](https://docs.docker.com/engine/storage/drivers/) and [shared/unique disk accounting](https://docs.docker.com/reference/cli/docker/system/df/) (accessed 2026-10-02). No live resource benchmark was run. Ready for owner discussion; implementation needs the current generic submission boundary mapped to this capability and scoped authorization.

**Next proof within LAT-08A:** create ten disposable submissions; measure incremental disk including host worktrees/data and Docker cache; open two, verify runtime cap/idle stop/restart, data isolation/reset, unchanged digest and failed-build states; close one and prove scoped cleanup preserves open candidates and review evidence. Measure schema/dependency changes too. A large observed unique-layer cost or slow wake-up would reverse the proposed retention/concurrency defaults.

**Retrospective:** observed friction was the legacy/generic path split, already identified by T03-CODE; reviewing those contracts avoided proposing a third preview mechanism. The applied process change separates artifact and runtime budgets in the handoff; source inspection supports that separation, while effectiveness at ten reviews remains hypothetical. This refines LAT-08A and PP-01D/E without closing their gates or changing roadmap order. Fixture ownership is clarified above; retention duration and measured capacity remain trial questions. No runtime code or live data changed.


## Shared integration and guided review requirements (2026-10-02)

### Implementation authorization and readiness

- **2026-10-02, owner chat:** “alright, go ahead and implement”. Authorized: bounded local implementation of shared integration for repository-writing layer Work, on-demand combined Code previews and guided scenario buttons, local tests/previews and durable evidence. No external writes, provider spending, public deployment or live-data acceptance. Preserve unrelated owner changes.
- **Process applied:** map the current generic submission, review and acceptance contracts before changing them; test the integrated result and acceptance race on disposable repositories. Reuse existing candidate/runtime boundaries and installed template contracts. Scenario setup must be pinned and preview-only. Implementation readiness is being assessed from source, with concrete gaps recorded during this run; no packet completion is claimed before checks and retrospective.

**Owner requirements:** every installed layer owns a repository, so integration before review applies to all repository-writing Work. For Code previews, the owner wants a button for each review step that opens exactly the relevant state without manual login or navigation. The [T03-CODE run log](t03-code-brief.md#run-log) records bounded planning scope; the implementation authorization above supersedes the earlier planning-only scope.

**Shared integration contract:** pin the original submission and its base, then create a separate integration candidate against the latest accepted head of each affected repository before presenting the proposed result for acceptance. Preserve original commits and review history. A conflict routes to explicit resolution/revision; a clean merge still runs the owning layer's applicable validators/checks. Documentation-only changes need their relevant validation, not an unnecessary app build. Structured record changes retain expected-revision validation; Git integration does not replace it. Consumed Library revisions are checked as well. For mixed source/record changes, retain DEC-056's coordinated pin/output/Work acceptance boundary; do not imply Git provides atomic multi-repository commits.

**Acceptance:** serialize integration acceptance per repository and atomically verify the reviewed base still matches the accepted head before advancing it. Accept the exact reviewed integration commit and associated output revisions. If a head or relevant consumed input changed, retain the old evidence and prepare a new review revision; no silent conflict repair or merge on Accept. Reuse still-identical build/check evidence. A reviewed approval never floats onto a different combined candidate. A conflict or failed preparation must still allow negative notes and send-back against the immutable submission, without authorizing acceptance. This capability belongs to the host/base-layer contract, with each installed layer providing its own validation and native review rendering.

**Guided Code preview:** each review step carries a stable ID, linked acceptance criterion, expected observation, compatible fixture/scenario revision, synthetic role/session, target route/entity and any required prerequisite app state. Show human-readable buttons such as “Review editing a published post.” Clicking a button prepares that step's isolated scenario, establishes the appropriate synthetic app session, and opens the exact page/entity/state in the candidate preview. A URL alone is insufficient for permission roles, modal/form state or workflows with prerequisite data. A project-defined preview adapter can prepare those states; unsupported steps show a clear unavailable reason rather than making the owner navigate manually. Anonymous and login-specific criteria may deliberately open their corresponding screen, without requiring login as preliminary setup for unrelated steps.

**State and identity:** demo sessions use the app's actual authorization paths for synthetic identities and remain confined to the isolated preview environment; portal sessions and real credentials never enter the candidate. Preview-only setup is disabled outside that environment. Named scenarios reset their own state deterministically; steps that intentionally continue a flow declare their order instead of resetting it unexpectedly. Reset and preview refresh preserve Work notes. Steps, scenario setup and observations are bound to the exact integration candidate/build; a refresh marks prior step observations as belonging to the old revision and requiring revalidation before they count for acceptance. Setup controls must not manufacture a successful criterion result: the reviewer still performs the behavior under review.

**Required evidence:** use two submissions from the same base on Code and a non-Code repository-writing layer. Accept one, show the other's integrated result includes it, and demonstrate clean-merge validation failure, textual conflict and a head-change race refusing acceptance. Verify a docs-only review avoids an app build. On a disposable Code preview, open two independently named review steps as different synthetic roles without manual login/navigation; verify exact entity/state, reset and ordered-flow behavior, notes retained, unavailable setup reported, no cross-candidate data/session reuse, and refresh invalidating previous observations. Verify preview-only setup is unavailable in the normal app environment.

**Handoff and retrospective:** this discussion exposed that Code-only integration framing and submission-time prebuilds were too narrow for the layer model and serial acceptance. The local proposal now separates original submissions from integrated review candidates for every repository-writing layer, and specifies repeatable scenario entry per review step. Documentation was checked for consistency; no runtime trial or owner usability acceptance is claimed. These are LAT-08A requirements, with app-environment support still depending on PP-01D. T03-CODE remains the next action; implementation readiness needs the current generic submission/acceptance boundaries and scenario adapter mapped and tested.
