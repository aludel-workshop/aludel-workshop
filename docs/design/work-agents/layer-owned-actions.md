# Layer-owned actions, shared Work

> **Superseded by DEC-057 (2026-09-30).** Work items are now layer-scoped: the item names its layer, the layer's charter and Knowledge replace per-action declarations, and authority is per layer (normal for members, explicit elevated grant for accepting reviews, deciding follow-ups and layer configuration). See [LAYER-SCOPED-WORK-01](../layer-scoped-work/work-record.md). The rest of this document is kept as history; its security boundary (host-checked writes and effects, human acceptance, no inferred grants) still applies.

## Decision and boundary

DEC-051 replaces Work roles as the owner of actions. A project installs layer instances; each layer declares its own versioned actions, methods and output adapters. A work item names the action's stable layer-qualified ID (`<layer>.<action>`), while its origin may be another layer, a person, a routine or an external observation. The action's layer determines its context and output authority. Work owns task intake, assignee, priority, dependencies, Go, pinned runs, questions, submissions, review signatures and history. The item-origin layer owns the review composition; each changed output still uses its own layer validator. Work does not define another layer's action or write its accepted output.

There is no required `role` record, role parent for an action, role-scoped instruction layer, or role lead as a permission grant in the target model. Project membership (`owner`/`member`), explicit layer/action grants, agent profiles and review signatures remain distinct. “Elevated” remains a visible property of an action, but is not a wildcard permission: the action must declare read and effect capabilities, and the gateway checks the actor, project, action revision and target on every operation. Code grants full reads of the bound project repository to authorized Work actions by default under DEC-054; candidate writes and other effects remain separately scoped and checked. A model, profile, task text, routine or layer policy cannot enlarge these capabilities. An elevated agent result still waits for a human reviewer with the required grant. The project owner retains the existing owner override; migrating role leads must produce explicit layer grants, never infer a grant from a same-named layer.

A layer may suggest Work from a source it does not own. The source is an exact input or observation, not a required story target. A direct human request may have no upstream artifact. Missing optional layers remain a named reduced mode or question, as in the [layer framework](../layer-framework/work-record.md). The current `pages.flows` adapter is still story-specific and is not the general contract.

## Declaration for each action

The owning layer supplies a stable local key and revision, title, purpose, output ledger, required/optional input roles, applicability, checks, method guidance, named read and effect capabilities, elevated flag, submission adapter, acceptance adapter and reviewer policy. A report can be a Work-owned review artifact; a change to a domain artifact must name its owning layer and output kind. Cross-layer effects require the other owner's adapter and grant, or a separate item when authorization or acceptance differs. The layer descriptor publishes the action list, but its text never grants capabilities by itself.

A compiled action ID is `<layer-key>.<local-key>`. A task also records `origin` (layer/routine/person/observation), source IDs and exact revisions, policy revision, action revision, intended output and expected reviewer. At Go, Work rejects a missing adapter, output kind, reviewer, or permission. It pins the action and input revisions in the same manifest read by solo agents and person-paired sessions. An already running attempt keeps its pin if an action definition changes; new work uses the new revision. A removed action becomes unavailable for new work while historical items and submissions remain readable.

Each action must distinguish `human`, `agent`, and unavailable execution. A human can use a layer action without an agent adapter if its human submission/review boundary exists. An agent is offered only when the exact output adapter, permissions and compatible profile/host are present. Human or agent assignment never grants Go. Every accepted domain change passes the owning layer's validator and DEC-050's checked run review. The existing ten-plus legacy actions are migration inputs, not the new catalog.

## Work style and initial assignment

Project work style remains a durable project setting: Dreamer, Planner or Tinkerer. It was chosen at onboarding and can later be changed in Settings. Each **newly installed layer** supplies an explicit human/agent initial-assignment choice per action and style. At installation, Work resolves `human` to the project owner or configured default person, and `agent` to an active default agent profile. If that performer or its adapter is unavailable, the action stays visibly unassigned/unavailable; installation does not silently choose a different performer. Elevated actions default to a human. A later explicit assignment may select a permitted agent and still requires elevated authorization and human review.

Changing the work style changes the seed for layers installed afterward. It does not reassign existing action defaults, work items, batches or running attempts. Each layer owns the per-action default-assignee control in its Operations/settings surface; Work may show a cross-layer assignment summary and lets a person change an individual task's assignee. `Work › Roles` and its role membership editor leave the target navigation. Work › Team keeps people and agent profiles; layer grants are shown as permissions, not as a second role taxonomy. The work style control belongs in project Settings, not a hidden onboarding-only preset. An installation record should retain the style and action revision used to seed defaults so later differences are explainable.

## Required migration and acceptance tests

1. **Inventory before conversion:** for each existing layer, map every legacy role action to a reviewed new action, split/retire it with reason, or mark it unavailable. Do not copy `roles.json` wholesale. Preserve old IDs and revisions for historical Work and runs. Active items either map under checked equivalence or remain Blocked for reassessment; never silently fall back to a different action.
2. **Permissions:** replace lead membership with explicit grants at the same or narrower scope; owner override remains. Test owner, granted member, ordinary member and agent against normal/elevated reads, file access, submit and accept. A migration cannot broaden access because a role name matched a layer key.
3. **Assignment:** install a layer under each work style and verify seeded human/agent choices, elevated human default, absent profile/adapter behavior and no reassignment after a style change. New layers use the current style; historical tasks keep their assignee.
4. **Execution:** compile a Go manifest from the layer action, verify exact output and source pins, ask a question on missing required context, submit a candidate, reject stale input, send back and accept only through the owning layer. Test a task with no story and a task originated by another layer.
5. **UI:** inspect action setup in the owning layer, the project work-style setting, default assignee and permissions, Work's cross-layer view, and the older task history. Confirm DEC-050's run/review composition survives.

The isolated candidate has a pure layer-action declaration validator as groundwork. It rejects duplicate/foreign outputs, undeclared reads/effects, invalid file scopes, mismatched adapters and an agent default without a runnable adapter. An action with no registered adapter stays unavailable and receives no default assignee. It does not replace the live role/action storage or enforce runtime permissions. DEC-053 confirms that LAT-06 compiles and pins its inventory locally; LAT-08 installs scoped grants, enforces exact repository/effect boundaries, seeds assignees and migrates historical roles before runtime permission claims. LAT-06 recreates Pages, Vision and the Code observation action against this contract; LAT-07 recreates the other built-in layer actions. A later explicit packet migrates persisted role/action records and UI only after the declarations and permission matrix pass. Arbitrary installed layers need a registered output schema, validator, adapter, permissions, migration/export and renderer; a free-form action definition cannot introduce a new effect.

## Process result and limits

This contract separates the reusable security and Work boundary from each layer's action inventory. The pure validator is evidence that declarations can be checked before installation; it is not proof of runtime enforcement, UX quality or action usefulness. The first Pages live turn proves a legacy adapter can submit a proposal into shared Work, but its title-only story does not approve the new action inventory. Reassess action names and checks with each layer's actual owner job and outputs during LAT conversion.

## DEC-054 review and repository-read update (2026-09-29)

The layer that creates a Work item owns its review composition, even when its evidence comes from another layer. Each changed output is validated by its owning layer. Shared Work retains Go, attempts, criteria, reviewer signature and atomic accept/reject. Pin the origin layer and affected output revisions at Go; [LAT-08A](../layer-app-transition/layer-owned-review.md) reuses changed native tabs in review. Code owns the repository read gateway. LAT-08's simple default permits an authorized project Work action to read its bound project repository without per-action file path lists; project isolation and secret exclusions still hold, and writes/effects retain explicit checks. Earlier path-scope examples describe the pre-migration declaration experiment, not the DEC-054 runtime default.
