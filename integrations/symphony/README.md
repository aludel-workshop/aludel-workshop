# Aludel tracker overlay for Symphony

Target: OpenAI Symphony commit `be10a1b79df723d6d7612b5651c8522704dafb2e` (R-06A pin). This is a local integration overlay, not a vendored copy. Its supervised disposable candidate path has live evidence. Real-work Go now uses explicit Symphony adapters; Go can queue while the host is offline; a recent authenticated poll is required for admission.

Copy `elixir/lib/symphony_elixir/aludel/adapter.ex` into the same path in an isolated Symphony checkout at that commit. From the checkout root, apply both `profile-turn.patch` and `runtime-block.patch` with `git apply`. The first adds Codex App Server `turn/start` model and effort overrides from each Go-pinned issue; the second registers the Aludel tracker and reports Symphony core blocked sessions back to the Work item. Check the pinned revision and patch applicability before starting the host. The adapter reports profile override support on every poll, so an older host cannot claim a profile that needs it. The Codex App Server protocol documents the per-turn fields at [the official App Server guide](https://developers.openai.com/codex/app-server/).

Start from [WORKFLOW.example.md](WORKFLOW.example.md), with one Symphony service per project pool. Set `tracker.provider.endpoint` in each workflow to the portal address reachable **from inside the host**; `ALUDEL_WORKER_URL` is separately used by the workspace hook. The example’s `127.0.0.1` works only when the host and portal share a network namespace. In the local Docker Desktop setup, the host uses `aludel.localhost` mapped to the Docker gateway and the adapter permits that local HTTP name. The portal creates a private project credential at `.data/symphony/<project-id>/worker-token` (or under `MACHINE_DATA_DIR`) and reuses it across restarts. Set `ALUDEL_WORKER_TOKEN_FILE` to that path in the trusted host; the adapter and workspace hook read it themselves. The owner never copies or pairs a token in Work. The adapter strips both token environment names from Codex child sessions. Configure `ALUDEL_WORKER_URL` as the portal worker API base, `ALUDEL_SOURCE_REPOSITORY` as the local project repository, `ALUDEL_WORKSPACE_HOOK` as the absolute path to `workspace-hook.mjs`, and `SYMPHONY_WORKSPACE_ROOT` as an isolated directory. Set the portal `MACHINE_SYMPHONY_WORKSPACE_ROOT` to that same absolute directory. The host-side `prepare` hook clones the project and checks out the exact Go-pinned commit; `start-run` registers the preserved workspace and reserves one run in Aludel before Codex starts. Set a stable, unique `ALUDEL_HOST_ID` for each host; the local launcher uses its container name. The portal binds an attempt to the first registered host ID, so another host cannot start a second turn from the same shared workspace. If the owning host is lost, resolve the item with a fresh Go rather than reusing its uncertain attempt. Both reject a changed base. The example requires `agent.max_turns: 1`; the adapter refuses polling under a multi-turn setting.

The host reports `agent.max_concurrent_agents` on authenticated polls. Deploy › Agent runtime sets Aludel's project capacity ceiling; the smaller of that ceiling and the host-reported capacity controls admission. To run a three-slot batch, configure at least three concurrent agents in both places. One host may execute batches for different profiles in sequence or in parallel; each attempt receives its pinned profile/role/action card. Codex profiles can select a model and effort per task when the host reports the `profile-turn.patch` capability; otherwise those batches wait in the authorized queue. The host still launches Codex from one global command, while other provider profiles remain saved but cannot Go until a compatible provider adapter is installed. Local host installation/start is automated by `local-hosts`; production host management and multi-host claim fencing remain open. Deploy reports an offline host rather than pretending it is connected.

The authenticated pool polls `GET /api/worker/issues?states=Ready` and refreshes exact IDs through `?ids=...`. Its `aludel_task_open` tool fetches a compact currently authorized task card by digest. `aludel_knowledge_map`, `aludel_knowledge_search` and `aludel_knowledge_read` provide bounded project-scoped discovery; `aludel_task_context` remains available for coding detail. Because the tested Codex sandbox makes `.git` read only, the agent calls `aludel_commit_candidate` after editing and checking code. The trusted host validates action-permitted paths and the pinned base, commits in the registered workspace, snapshots that exact commit into Aludel-owned storage, and submits it. Symphony may delete its workspace as soon as the issue reaches Submitted, so review and acceptance use Aludel's retained snapshot. `aludel_submit_candidate` remains available for an existing valid commit in that same workspace. A layer-scoped task (DEC-057) changes its layer's data only through `aludel_layer_call` (`operation`, optional path `id`, `body`), which the host validates against the layer's OpenAPI document and stages for review. It then submits notes and follow-ups with `aludel_submit_proposal`. The workspace hook also checks out the layer instance's own repository in `layer/` on the run's work branch, with a copy of the layer's current outputs in `layer/.aludel/outputs/`; the agent edits and tests there, then calls `aludel_layer_commit` (`message`, `tests`) and the host commits and fetches that branch. Accepting the review applies the staged data and merges the branch. Both tools compile under `--warnings-as-errors` at the pin, upstream's suite passes with the overlay, and [`layer-tools-check/`](layer-tools-check/) drives them through the compiled adapter against a disposable portal (hook, calls, commit, submit, owner acceptance and merge) without a model turn. A live Codex turn on a layer-scoped task has not yet run. Agent-reported checks require `name` and `status` (`passed`, `failed`, or `skipped`), with optional `detail`. They are claims; they do not satisfy owner review or close Work.

Before a live Go, verify the four host paths/variables (`ALUDEL_WORKER_URL`, `ALUDEL_SOURCE_REPOSITORY`, `ALUDEL_WORKSPACE_HOOK`, `SYMPHONY_WORKSPACE_ROOT`), a writable Symphony `--logs-root`, and a clean source commit. Run `codex -c 'service_tier="fast"' login status` or the equivalent for the installed CLI and a no-turn App Server `initialize`/`thread/start` check. A successful handshake does not prove `turn/start` or model execution. Capture a redacted error trace in a writable local log, and limit retries to the authorized number of coding turns. `agent.max_turns` limits a single Symphony run. The Aludel tracker requires it to equal one, while the worker atomically reserves up to three runs per Go-pinned attempt; an uncertain or failed start consumes its reservation. Exhausted work leaves Ready polling but retains final-run context and submission access. This limits turns, not tokens or spending. The owner-authorized live trial still used an independent one-process guard. [Local budget and recovery evidence](../../docs/evidence/lay-05-budget-recovery.md).

Explicit output adapters and their current evidence are listed in [the Symphony swap record](../../docs/evidence/work-agents-01-symphony-swap.md). Other role actions remain gated until their output and acceptance boundaries are implemented.


Runtime failures use the Work execution-block contract. A queued task whose project host is offline or cannot apply the pinned profile is projected as **Blocked** with an **Open Deploy** recovery action and clears automatically when host readiness returns. A changed Go snapshot or a trusted workspace-hook/runtime `blocked` or `error` event persists a concise reason on the item; retrying by staging or authorizing the replacement batch clears that prior block. Dependency blocking remains the separate **Blocked by W-n** relationship.


## Reboot-safe local startup

When local `.env` sets `MACHINE_SYMPHONY_DISPATCH=1`, `./launch-machine` now invokes `integrations/symphony/local-hosts` after the portal build. The command derives configured project pools from the portal database, reuses or builds the pinned upstream revision plus checked-in overlays, installs Codex 0.157 in an isolated directory, generates one workflow per pool, and reconciles exact `aludel-symphony-<project>` containers. Generated source, dependencies, workflows, logs and writable Codex state live under ignored `MACHINE_DATA_DIR/symphony-host`, not `/tmp`; the existing Codex auth file and project-pool credentials remain read-only mounts. Containers retain `unless-stopped` restart policy. Codex's inner Bubblewrap command sandbox requires unprivileged user namespaces, which Docker's default seccomp profile denies in this environment. Local workers therefore run with `seccomp=unconfined` plus `no-new-privileges`, without privileged mode or added capabilities; source, credentials and auth remain read-only mounts. Startup executes a no-model Bubblewrap namespace smoke test and refuses to report the worker started if it fails.

The first setup needs Docker and network access to the official Symphony Git repository, Hex packages and the pinned Codex npm package. Later starts reuse the content-addressed build. Run `integrations/symphony/local-hosts --verify` for an operator check that waits for a fresh authenticated heartbeat from every configured pool. If host reconciliation fails, `launch-machine` still starts the portal, where authorized work remains Blocked with its Deploy recovery route; the launcher prints the host failure separately from the portal dispatch-admission state. The pinned upstream implementation is evaluation-only and its resolved dependencies currently report security advisories, so this remains a local trusted-host path, not a production deployment pattern.
